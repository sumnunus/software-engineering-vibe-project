# Lessons Learned

## 문서 개요

- 프로젝트명: ReadyGo
- 작성일: 2026-06-04
- 작성 목적: 요구사항 분석에서 품질 관리에 이르기까지 소프트웨어공학 프로세스를 적용하며 얻은 교훈과, 프로세스에 입각한 바이브코딩의 효과 및 한계를 정리한다.

## 프로젝트 요약

ReadyGo는 아침 외출 준비 과정에서 필요한 준비물, 날씨, 기온별 옷차림, 관심 정류장 버스 도착 정보, 외출 시각까지 남은 시간을 한 화면에서 확인할 수 있도록 만든 웹앱이다. 프로젝트는 개인 단위로 수행했으며, 인공지능을 요구사항 정리, 설계 보조, 코드 작성 보조, 테스트 케이스 정리, 문서화에 활용하였다.

이번 프로젝트의 핵심은 단순히 AI에게 코드를 생성하게 하는 것이 아니라, 요구사항 분석, 설계, 구현, 테스트, 배포, 품질 개선이라는 소프트웨어공학 프로세스를 유지하면서 AI를 협업 도구로 사용하는 것이었다.

## 프로세스에 입각한 바이브코딩의 효과

### 요구사항 분석 단계

바이브코딩을 바로 시작했다면 “외출 준비 앱”이라는 아이디어만으로 화면을 만들었을 가능성이 높다. 그러나 요구사항 분석을 먼저 수행하면서 사용자가 실제로 아침에 겪는 문제를 구체화할 수 있었다. 특히 외출까지 남은 시간, 준비물, 날씨, 버스 정보의 우선순위를 정하면서 화면 구조의 기준이 생겼다.

AI는 이 단계에서 누락될 수 있는 요구사항을 점검하는 데 효과적이었다. 예를 들어 단순히 “준비물 표시”가 아니라 추가, 수정, 삭제, 체크, 체크해제까지 기능 요구사항으로 분리하도록 도와주었다. 그 결과 구현 중 기능 범위가 흔들리는 일이 줄어들었다.

다만 요구사항 분석에서도 최종 판단은 프로젝트 수행자가 해야 한다는 점을 배웠다. AI는 가능한 기능을 많이 제안하는 경향이 있었고, 모든 기능을 수용하면 프로젝트 범위가 과도해질 수 있었다. 따라서 Must, Should, Could와 같은 우선순위 기준을 두는 것이 중요했다.

### 설계 단계

설계 문서를 작성하면서 컴포넌트와 모듈의 책임을 먼저 분리한 것이 구현 효율을 높였다. 날씨 조회는 `weatherService`, 버스 조회는 `busService`, 저장 기능은 `storageService`, 시간 계산은 `timeUtils`, 옷차림 추천은 `outfitRules`로 분리하였다.

이러한 구조는 소프트웨어공학에서 배운 추상화, 캡슐화, 모듈화, 낮은 결합도와 높은 응집도를 적용한 결과이다. 예를 들어 버스 API 연동이 처음에 실패했을 때도 UI 전체를 다시 작성하지 않고 `busService`와 mock fallback 전략을 중심으로 문제를 처리할 수 있었다.

설계 단계에서 프로세스를 따른 효과는 유지보수성에서 나타났다. 기능을 추가할 때마다 기존 코드를 크게 흔들지 않고 필요한 모듈만 수정할 수 있었다. 이는 개발 속도뿐 아니라 결함 수정 속도도 높였다.

### 구현 단계

구현 단계에서 AI는 반복적인 코드 작성 시간을 줄이는 데 큰 도움이 되었다. 투두 추가/수정/삭제, 외출 시각 계산, API 응답 정규화, CSS 조정처럼 세부 구현이 많은 작업에서 빠르게 초안을 만들 수 있었다.

하지만 AI가 생성한 코드가 항상 사용자의 맥락에 맞는 것은 아니었다. 예를 들어 삭제 확인 UI는 처음에는 버튼 크기와 취소 흐름이 어색했고, 날씨 아이콘 정렬이나 외출 시각 게이지 색상도 실제 화면에서 확인한 뒤 조정이 필요했다. 이 경험을 통해 바이브코딩은 “한 번에 완성하는 방식”이 아니라 “생성, 검토, 수정, 재검증을 빠르게 반복하는 방식”에 가깝다는 점을 배웠다.

구현 속도는 확실히 절약되었다. 특히 기능 초안 작성과 문서 초안 작성에서 시간이 줄었다. 그러나 절약된 시간이 곧바로 최종 완성 시간 단축으로만 이어지지는 않았다. AI가 만든 결과를 검토하고, 실제 사용 맥락에 맞게 다듬고, 테스트하는 시간이 반드시 필요했다. 따라서 바이브코딩의 효과는 “검증 없는 자동화”가 아니라 “반복 개선 속도 향상”으로 이해하는 것이 더 정확하다.

## 테스트 및 품질 관리에서 얻은 교훈

테스트 보고서를 작성하면서 요구사항 ID와 테스트 케이스를 연결한 것이 유용했다. 기능이 실제로 구현되었는지 단순히 눈으로 확인하는 데서 끝나지 않고, 어떤 요구사항을 어떤 방식으로 검증했는지 추적할 수 있었다.

로컬 테스트와 배포 환경 테스트를 분리한 것도 중요했다. 로컬에서는 Vite proxy를 통해 버스 API가 정상 동작했지만, Vercel 배포 환경에서는 서버리스 함수의 catch-all 경로 파라미터를 제대로 읽지 못하는 문제가 발생했다. 이 문제는 배포 환경에서만 발견되었고, 요청 URL의 pathname을 기준으로 엔드포인트를 복원하도록 수정하여 해결하였다.

이 경험을 통해 “로컬에서 된다”는 것이 곧 “배포 환경에서도 된다”는 뜻은 아니라는 점을 배웠다. 특히 API 인증키, 환경 변수, 서버리스 함수, CORS, 배포 플랫폼의 라우팅 방식은 실제 배포 후 반드시 검증해야 한다.

품질 관리 측면에서 가장 큰 교훈은 UI도 테스트 대상이라는 점이었다. 기능이 동작하더라도 사용자가 휴대폰에서 보기에 화면이 너무 크거나 스크롤이 길면 만족도가 떨어질 수 있다. ReadyGo는 본질적으로 아침에 빠르게 확인하는 앱에 가까운 서비스이므로, 웹앱으로 구현하더라도 모바일 화면에서 한눈에 보이는지 확인해야 했다. 이후 모바일 compact 레이아웃을 적용하여 작은 화면에서도 전체 대시보드가 한 화면 안에 들어오도록 개선하였다.

## 백엔드 서비스 의존의 문제

이번 프로젝트에서는 날씨 API와 서울 버스 API라는 외부 서비스를 사용하였다. 외부 API를 사용하면 직접 데이터를 구축하지 않아도 실제 정보를 제공할 수 있다는 장점이 있다. 그러나 동시에 백엔드 또는 외부 서비스에 의존할 때의 한계도 분명히 드러났다.

첫째, 서울 버스 API는 서울특별시 버스 정보망을 기준으로 한다. 따라서 사용자가 실제로 타는 버스가 서울시 API 범위 밖의 노선이거나 다른 지자체 버스인 경우, 앱에 표시되지 않을 수 있다. 이는 앱 구현 오류라기보다 사용한 외부 API의 제공 범위에 따른 제약이다.

둘째, 인증키 승인과 API 응답 안정성에 영향을 받는다. 실제로 버스 API 인증키 적용 초기에는 인증 오류가 발생했고, 공공데이터포털 문의 후 재검증을 통해 해결하였다. 이 과정에서 외부 서비스 연동은 단순한 코드 구현뿐 아니라 승인 상태, 인증키 형식, 배포 환경 변수 설정까지 포함하는 품질 관리 대상임을 알게 되었다.

셋째, 서비스 범위를 명확히 사용자에게 알려야 한다. 현재 ReadyGo의 버스 정보는 “서울 버스 API 기준”이라는 전제가 있다. 향후 실제 서비스로 발전시키려면 경기버스, 광역버스 등 다른 교통 API를 추가하거나, 지원 범위를 UI와 문서에 명확히 표시해야 한다.

## 프로세스를 따랐을 때와 따르지 않았을 때의 비교

프로세스를 따랐을 때 가장 큰 장점은 작업 기준이 흔들리지 않았다는 점이다. 요구사항 분석에서 기능 범위와 우선순위를 정했고, 설계에서 모듈 책임을 나누었으며, 구현 후 테스트 보고서로 검증하였다. 그래서 중간에 UI 수정, API 오류, 배포 오류가 발생해도 어느 단계의 문제인지 구분할 수 있었다.

반대로 프로세스를 따르지 않고 바이브코딩만 했다면 초기 화면은 더 빨리 만들 수 있었을 것이다. 그러나 기능이 왜 필요한지, 어떤 요구사항을 만족하는지, 어떤 테스트로 검증했는지 설명하기 어려웠을 것이다. 특히 교수님이 요구한 “지속적인 토의와 형상 관리 증빙”을 만족하기 어려웠을 가능성이 높다.

이번 경험을 통해 프로세스는 개발을 느리게 만드는 절차가 아니라, AI가 만든 결과를 통제하고 검증 가능하게 만드는 장치라는 점을 배웠다. 바이브코딩은 빠른 구현을 가능하게 하지만, 소프트웨어공학 프로세스가 없으면 결과물이 우연히 잘 된 것인지 체계적으로 잘 된 것인지 판단하기 어렵다.

## 만족도와 성능에 대한 평가

이번 프로젝트에서 성능 향상은 주로 실행 속도보다는 개발 생산성과 사용 경험 측면에서 평가할 수 있다.

개발 생산성 측면에서는 AI를 활용하여 문서 초안, 코드 초안, 테스트 항목 작성 시간을 줄일 수 있었다. 특히 반복적인 UI 수정이나 API 응답 정규화 작업에서 빠른 제안을 받을 수 있어 개발 속도가 향상되었다.

사용자 만족도 측면에서는 기능별 피드백을 반영할수록 화면 완성도가 높아졌다. 예를 들어 외출 게이지 색상을 조정하고, 삭제 확인 UI를 개선하고, 날씨 카드의 아이콘 정렬을 수정하고, 모바일 compact 레이아웃을 적용하면서 실제 사용 맥락에 더 가까운 화면이 되었다. 이는 단순 기능 구현보다 반복적인 품질 개선이 만족도를 높인다는 점을 보여준다.

정량적인 성능 측정 도구를 사용하지는 않았지만, `npm run build`를 통해 프로덕션 빌드 가능 여부를 검증했고, 로컬과 Vercel Production 환경에서 API 응답을 확인하였다. 향후에는 Lighthouse, 접근성 검사, 모바일 성능 점수 등을 추가하여 사용성뿐 아니라 성능을 더 객관적으로 평가할 수 있다.

## 부족했던 프로세스

이번 프로젝트에서 부족했던 부분도 있었다. 일부는 프로젝트 후반에 보완했지만, 일부는 향후 개선 과제로 남았다.

첫째, 모바일 우선 설계가 충분하지 않았다. ReadyGo는 실제로 휴대폰에서 사용하기 적합한 서비스인데, 초기 UI는 데스크톱 화면에서 먼저 다듬어졌다. 그 결과 배포 후 휴대폰에서 열었을 때 카드와 글자가 너무 크게 보이는 문제가 있었다. 이후 모바일 compact 레이아웃으로 보완했지만, 처음부터 모바일 화면을 주요 기준으로 설계했다면 더 자연스러운 결과를 얻을 수 있었을 것이다.

둘째, 외부 API 범위 검토가 충분하지 않았다. 서울 버스 API를 사용하면 서울 버스 정보만 안정적으로 제공된다는 점을 뒤늦게 더 명확히 인식했다. 요구사항 분석 단계에서 “지원 교통 범위”를 더 구체적으로 정의했다면 사용자의 기대와 실제 API 범위 사이의 차이를 줄일 수 있었을 것이다.

셋째, 자동화 테스트가 부족했다. 이번 프로젝트는 수동 테스트와 빌드 검증 중심으로 품질을 확인하였다. 시간 계산이나 옷차림 추천 같은 순수 함수는 자동 테스트로 검증하기 적합했지만, 별도의 테스트 프레임워크를 도입하지는 않았다. 향후에는 Vitest 등을 도입해 핵심 로직을 자동 테스트하면 변경 후 회귀 결함을 더 빠르게 발견할 수 있다.

넷째, 배포 환경을 초기에 고려하지 못했다. 로컬에서는 Vite proxy로 버스 API가 동작했지만, 배포 환경에서는 별도의 서버리스 함수가 필요했다. 향후에는 설계 단계에서 로컬 실행 방식과 배포 실행 방식을 함께 정의해야 한다.

## 프로젝트 중 보완한 방식

부족했던 부분 중 일부는 프로젝트 후반에 다음과 같이 보완하였다.

- API 인증키 노출을 막기 위해 Vercel 서버리스 함수로 서울 버스 API를 중계하였다.
- 로컬 테스트뿐 아니라 Vercel Production 배포 환경에서도 API 응답을 확인하였다.
- 테스트 보고서에 요구사항 ID, 테스트 케이스, 결함, 재검증 결과를 연결하였다.
- 모바일 화면에서 전체 대시보드가 한 화면에 들어오도록 compact 레이아웃을 추가하였다.
- 외부 API의 제공 범위 한계를 lessons learned와 최종 보고서에 반영할 수 있도록 정리하였다.

이러한 보완을 통해 단순히 “코드가 돌아가는 상태”에서 끝나지 않고, 실제 사용 환경과 제출 요구사항을 함께 고려하는 방향으로 품질을 높일 수 있었다. 다만 서울 버스 API의 제공 범위 한계와 자동화 테스트 부족은 완전히 해결된 것이 아니라, 향후 개선 과제로 남겨야 한다.

## 종합 교훈

이번 프로젝트를 통해 프로세스에 입각한 바이브코딩은 빠른 구현과 체계적인 품질 관리를 함께 가능하게 한다는 점을 배웠다. AI는 요구사항 정리, 설계 아이디어, 코드 작성, 테스트 문서화에서 생산성을 높여주었지만, 프로젝트 방향 결정, 범위 조정, 품질 판단, 최종 검증은 수행자의 책임이었다.

따라서 바이브코딩의 효과는 AI가 코드를 대신 작성해준다는 데에만 있지 않다. 더 중요한 효과는 수행자가 소프트웨어공학 프로세스를 유지한 상태에서 AI를 반복적인 사고와 구현의 보조 도구로 활용할 수 있다는 점이다. 요구사항 분석, 설계, 구현, 테스트, 배포, 회고가 연결되어 있을 때 AI가 만든 결과도 설명 가능하고 검증 가능한 소프트웨어 산출물이 된다.

ReadyGo 프로젝트에서는 프로세스를 따른 덕분에 기능 구현뿐 아니라 GitHub issue, commit, 회의록, 테스트 보고서, 배포 URL이라는 증빙을 남길 수 있었다.
